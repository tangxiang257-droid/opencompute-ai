# OpenCompute AI v0.4.6 — 单 Rank 快路径、重复测量与 TP / PP 方案筛选

## 本轮解决什么问题

v0.4.5 已用微型合成 Qwen2 证明：**2 Rank TP 可以保证数值结果正确，但不代表比 1 Rank 更快。** 下一步必须验证测量稳定性，并区分通信优化与并行架构重设计。本版本继续在受信任的**单台 GitHub Linux CPU 主机**测试，不下载 DeepSeek 官方权重、不购买服务器、不模拟成真实跨物理设备的结果。

## 代码变化

### 1. 单 Rank 正确性保持的低风险通信快路径

`compute/qwen2_generate.py` 单 Rank 默认避开没有真实远端参与者的 `dist.broadcast`、`dist.all_reduce` 以及报告用的 `dist.all_gather`。仍然使用已有 Qwen2 数值计算、Gloo 初始化、参数校验与完整稠密参考对照。对应 profiler 将 `local_single_rank_collectives_skipped=true` 并记录 **0 次**正式 decode Collective。

用 `--no-single-rank-fastpath` 反向禁用优化，作为与旧实现等价的性能 A/B 基准。**双 Rank 不会省略两次每层每生成步骤的 All-Reduce**：注意力输出与 MLP 残差之间存在真实依赖，直接删除同步会导致错误。关于双 Rank 降低通信，需要后续尝试减少跨网络的并行边界、流水线、计算融合等更重大架构改变。

### 2. 重复的性能矩阵和统计口径

`benchmarks/qwen2_repeat_v046.py` 实现三组相同随机权重、相同 Prompt、相同 Token 数的比较：

- `local_fastpath`：1 Rank，关闭无意义 Collective；
- `legacy_collective`：1 Rank，显式执行旧式无意义 Collective；
- `tensor_parallel`：2 Rank，真实 Gloo Rank 间协作。

每组 **2 至 10 次**有效测量，另可选择 0 至 2 轮操作系统缓存预热；每轮会轮换三个模式的执行顺序。输出原始逐轮数据、耗时中位数、最小/最大、最邻近秩 p10/p90 和样本标准差、每 Rank Collective 时间占比和 Linux 单进程 RSS 峰值。

**重要：** 每个样本都启动新 `torchrun` 进程组。这里的预热是主机/文件系统缓存预热，不代表同一存活推理服务中的算子预热或长时间吞吐。重复测量可减轻单次抖动，但 2–3 个样本**不足以获得统计置信区间**。性能加速系数为两种模式耗时的**样本中位数比值**，不宣称有显著性或稳定跨机器收益。完整启动时间和 decode 耗时分别呈现。

示例（仅在可信本机）：

```bash
python -m benchmarks.qwen2_repeat_v046 \
  --model-size tiny --dtype float32 \
  --repeats 3 --warmups 1 --tokens 3 \
  --output qwen2-v046-repeat.json
```

性能文件使用 `opencompute-qwen2-repeated-v046` schema，拒绝覆盖已有输出。测试模型有 `tiny` 和 `small` 两种内置合成结构；不需要联网下载真实权重。CI 会以低成本 `tiny` 版本生成 artifact，便于核查每一次样本与峰值。

### 3. TP 与流水线并行 PP 的可行性筛选——仅数学规划器

`compute/parallel_screen_v046.py` 依据模型层数、Q/KV heads、权重估算、节点可用内存、网络延迟/带宽、上下文长度，输出两种模式的：

- 权重**下限**内存占用（不包含 KV Cache、Python/PyTorch 运行时、加载峰值和激活内存）；
- TP head / KV head 是否可以被设备数整除；PP 的层数是否足够分配；
- TP 的**示例性环形 All-Reduce 网络成本代理量**与 PP 的**边界传输代理量**；
- PP 未实现、单路自回归解码有阶段间串行依赖、必须执行实测的声明。

下列数据不等于 Gloo 实际 wire traffic，也不能拿一个延迟/带宽假设宣称真实 WAN Token/s。PP 在未来可能帮助较少跨节点通信的场景或多请求吞吐，但在单条自回归请求下，层间依赖并不会因拆分就自动加速。本阶段**没有实现真正 PP Worker**。

### 4. 自动化测试

- `tests/test_qwen2_validation_v045.py` 修正单 Rank 快路径下的期望通信次数，双 Rank 仍保留真实 All-Reduce 和广播计数核验。
- `tests/test_qwen2_repeat_v046.py` 验证单 Rank/双 Rank 模式区分、样本统计边界、模型/拓扑约束、假设示例的保守报告与恶意/错误输入拒绝。
- `.github/workflows/cluster-v03.yml` 新增 v0.4.6 专项测试及实际重复 Gloo 测量，并将完整结果保存为 `opencompute-qwen2-v046-repeated-gloo` Artifact，保留 7 天。

## 验证逻辑和真正的验收条件

每次运行先从同一个随机种子生成 Qwen2 合成权重，导出可信本地 Safetensors 供 1/2 Rank 使用。所有模式都必须和经过相同精度舍入的**单机稠密计算参考**做逐步 Logits 和 Token ID 比较。任意一次不一致直接导致基准失败，不能把坏结果也纳入性能统计。

**验收标准**：最新带有 v0.4.6 的 commit 对应 GitHub Actions CPU 全量测试成功，集群专项测试成功，重复基准完成并上传 JSON 文件，且单 Rank 优化及双 Rank 均通过数值一致性检查。旧提交的绿色状态不能冒充新提交验收成功。

## 下一步和限制

- 暂未真实跑 DeepSeek-R1-Distill-Qwen-1.5B 官方完整预训练权重，因此没有真实 DeepSeek 的 Token/s、真实精度与可用内存结论。
- 尚无真正双物理设备连接、GPU 通信、网络加密、流水线并行引擎和跨设备故障处理验收。
- 若重复试验继续发现 2 Rank TP 显著慢于单 Rank，应优先研究 PP 原型、节点亲和性/分层通信和更大的**可信本机**模型基准，而不是假定公网算力池的 Token/s 会提升。
- “内存聚合可行性”与“速度提升”必须分开验收；真实互联带宽与稳定性需要未来的设备实测。

本版的目标是建立**诚实、可重复的决策依据**，而不是把多卡、多节点、更大模型一概说成加速。
