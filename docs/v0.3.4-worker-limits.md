# OpenCompute AI v0.3.4 — local CPU Worker resource safeguards

This revision adds limits to the **trusted, single-machine research prototype**. It does not enable internet-scale inference or untrusted computation.

## Protection layers

| Layer | Default | Actual guarantee |
|---|---|---|
| Managed child CPU-time limit | POSIX `RLIMIT_CPU`, `ceil(wall_timeout)+30` seconds | OS-enforced **per-process CPU time**, not CPU utilization or entire process-tree CPU quota |
| Parent wall-clock timeout | Existing 150-second watchdog | Kills POSIX process group after timeout, best effort |
| Parent process-tree RSS budget | Estimated `reserved_memory_mb`, checked at 1-second intervals | **Reactive** RSS watchdog; not a hard allocation limit and cannot prevent sub-second OOM |
| Strict monitoring option | `OPENCOMPUTE_TP_REQUIRE_RSS_MONITOR=1` | Fails a rank if RSS observation cannot be performed |
| Optional virtual-address-space cap | `OPENCOMPUTE_TP_MAX_VMEM_MIB` (unset by default) | POSIX `RLIMIT_AS`; enforced *virtual* memory allocation cap, **not physical RAM** |
| Docker local TP lab | Optional, not default | Docker engine CPU/memory/PID cgroup quotas with host-loopback Gloo access on Linux |

The coordinator now includes `reserved_memory_mb` in each authenticated rank assignment. The rank agent passes that value into a process-tree RSS monitor; if exceeded, it terminates its Gloo process group, sends a failure to the coordinator and allows the existing failed-session cleanup/retry protocol to apply.

### Why RLIMIT_AS is off by default

PyTorch may reserve much more virtual address space than its actual physical RSS, even with a tiny CPU model. Enforcing `RLIMIT_AS=512 MiB` can falsely prevent initialization. Set it only after studying the operating system and model memory requirements. For actual enforceable **physical** RAM limits prefer Linux cgroups / Docker's `mem_limit` over `RLIMIT_AS` or periodic RSS sampling.

### Child launcher (no arbitrary execution)

The Worker now starts the **fixed** module `python -m cluster_v031.limits --cpu-seconds ... -- --shards ...`. The launcher applies POSIX limits *before importing PyTorch*, then executes only `compute.gpt2_generate` using Python's module mechanism. It cannot accept a shell command or a user-selected Python module.

The Worker still runs as a trusted local process. Neither the fixed module nor Docker quotas make model weights safe to load from an untrusted provider.

## Optional same-machine Docker layout (Linux only)

The default `docker-compose.yml` continues to start the older light CPU task Workers; it **does not** participate in GPT-2 TP. A separate, explicitly opt-in file, `docker-compose.tp-local.yml`, provides two **real TP Workers** and a localhost coordinator:

- Uses `network_mode: host` on Linux so all three containers can connect to the same `127.0.0.1` PyTorch TCPStore. This setting weakens network isolation and **must not be used with untrusted Workers**.
- Coordinator binds the management API to `127.0.0.1:8000`. No publicly bound API port is configured by this file.
- Each Worker has an independent writable shard cache volume; container filesystem is otherwise read-only.
- Each Worker has Docker `mem_limit: 2g`, `cpus: 1`, `pids_limit: 128`, dropped Linux capabilities and `no-new-privileges`.
- Coordinator has `mem_limit: 4g` and `cpus: 2`; its database/model folders are mounted separately.
- Docker must support the requested resource restrictions and host network; Docker Desktop and rootless environments may behave differently.

**Do not start it together with the default Compose stack on port 8000.** The optional file has not been validated on a real external host and should not be presented as production-ready.

Example for a future trusted local test, not run in this development turn:

```bash
cp .env.example .env
# replace both OPENCOMPUTE_ADMIN_KEY and OPENCOMPUTE_JOIN_KEY
# with independent long random strings before any start
docker compose -f docker-compose.tp-local.yml config --quiet
docker compose -f docker-compose.tp-local.yml up --build -d
```

A further same-machine experiment would be required to certify the combination of Docker bridge/host settings, kernel limits and Gloo startup in a particular environment. **No cross-physical-device experiment was run for this milestone.**

## Guardrails and CI tests

```bash
python -m unittest discover -s tests -p 'test_resource_limits_v034.py' -v
python -m unittest discover -s tests -v
```

New tests use mocked `resource.setrlimit`, `psutil.Process` and synthetic subprocess objects. They check CPU limit configuration, optional virtual address space configuration, RSS aggregation, over-budget termination and fixed module launch.

The GitHub Actions workflow runs these alongside existing v0.3.1/v0.3.3 tests and local synthetic HTTP/Gloo smoke checks. A test file committed to GitHub is **not** evidence that the latest CI execution has passed; inspect the Actions run conclusion.

## Remaining risks and priorities

1. **Internet/remote node security**: no mTLS, node attestation, untrusted checkpoint sandbox, fair-use accounting or result verification. Do not expose service to the public internet.
2. **Fast memory spikes**: RSS polling has a finite observation delay; run the optional container with real Docker memory limits when strong host-level RAM containment is needed.
3. **CPU quota**: RLIMIT_CPU is per process. Docker CPU cgroup quotas regulate the container as a group; neither ensures strict latency fairness under contention.
4. **Distributed retry**: currently restarts from the original prompt with fresh Gloo ranks. No KV-cache restoration, no checkpoint/restart at token boundaries, and no seamless live rank replacement.
5. **Storage/weight provenance**: cached shards are copied by session ID; SHA-256 checks transport integrity, not trust or validation of original model weights.
6. **Local API/rendezvous**: coordinator still single-process, 127.0.0.1-only; Docker host network is for the trusted Linux same-machine setup only.
