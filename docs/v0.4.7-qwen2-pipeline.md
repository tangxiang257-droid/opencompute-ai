# OpenCompute AI v0.4.7 — 首个实际执行的 Qwen2 双阶段流水线（PP）

## 目标与边界

v0.4.6 只有张量并行（TP）与流水线并行（PP）的数学筛选。v0.4.7 首次实现真正的 **Gloo 双进程模型分层执行**，不是模拟阶段耗时。

本阶段只在可信 Linux/单机 torchrun 环境工作，使用官方 Qwen2 架构的离线 Safetensors 格式与现有的 FP32 CPU 计算核心。**没有接入公共调度器，不能在网站把 PP 标成正式可选的跨设备模型服务。** 不能将单机 PP 性能外推为两台设备、互联网或 GPU 的结果。

## 本轮真实代码

- `compute/qwen2_pipeline_v047.py`: 将已有完整 Qwen2 v2 **单 Rank** 检查点拆成独立的两份**完整层**文件，添加固定格式 `pipeline_manifest.json`、每文件 SHA-256、大小校验及 rank 文件隔离；使用 Gloo send/recv 真正传递隐藏张量。
- `benchmarks/qwen2_pp_compare_v047.py`: 相同合成随机权重、相同 Prompt、相同精度和相同生成 Token 的 TP1、TP2、PP2 计算结果和速度单次对比，产生 JSON。
- `tests/test_qwen2_pipeline_v047.py`: 验证层没有重复分布、Rank 0 独占 IO、篡改或软链接拒绝、损坏 Rank 启动预检查同步失败，以及 FP32/BF16 的逐 Token 完整 Logits 正确性。
- `tests/test_qwen2_pipeline_hf_v047.py`: 使用本地随机实例化的**独立 Hugging Face Qwen2ForCausalLM** 作 FP32/BF16 参考，不下载任何预训练权重。运行模型比较时 CI 必须显式要求 transformers，不能因 import 失败静默跳过。
- `.github/workflows/cluster-v03.yml`: 自动执行上述专项测试、TP1/TP2/PP2 对比，将 `qwen2-v047-tp-pp.json` 保留为 GitHub Actions Artifact。

## 执行和数据流

```text
Rank 0（前半 Transformer 层）                Rank 1（后半 Transformer 层）
  Prompt Token -> Embedding
            -> Layer 0..k-1
            -- 隐藏向量（dist.send） ------>  Layer k..n-1
            <-- 隐藏向量（dist.recv） ------  完成最后一层
  Final RMSNorm -> LM head
  argmax -> 新 Token
  下一步再次从 Rank 0 开始
```

Rank 0 持有全部词表 embedding、最终 RMSNorm 和 LM Head。Rank 1 只持有自己的 Transformer 层，不拥有词表权重。两端的 KV Cache 分别保存在各自持有的层对应的进程中，不伪装为可恢复的跨进程缓存。

当前仅支持 **两个 stage、单条自回归请求**。Rank 0 必须等待 Rank 1 返回每一步最终隐藏状态，因此单条请求的两个 stage **不能同时对同一个 Token 并行计算不同层**。PP 的主要优点首先是按层减少每台机器承载的 Transformer 权重，而不是保证降低单请求推理时延。未来若实现多请求流水线，可在不同请求的独立 KV Cache 管理和并发调度下研究吞吐收益。

## 命令（仅可信本机 CPU）

先导出一份你自己信任且符合 `opencompute-qwen2-tp-v2` 的 **workers=1** Qwen2 模型到 `/trusted/qwen2-v2-one-rank`。对于随机合成权重，可用现有 `compute.qwen2_shards.synthetic_state` + `compute.qwen2_chunked.export_chunked` 生成测试检查点。

```python
from compute.qwen2_shards import synthetic_state
from compute.qwen2_chunked import export_chunked
from compute.qwen2_pipeline_v047 import partition_one_rank_v2

state, config = synthetic_state(
    hidden=24, heads=6, kv_heads=2, layers=4,
    inner=48, vocab=64, positions=64)
export_chunked(state, config, "/tmp/qwen2-v2-one-rank",
               workers=1, chunk_rows=11, storage_dtype="float32")
partition_one_rank_v2("/tmp/qwen2-v2-one-rank", "/tmp/qwen2-pp")
```

```bash
python -m torch.distributed.run --standalone --nproc-per-node=2 \
  -m compute.qwen2_pipeline_v047 \
  --bundle /tmp/qwen2-pp --prompt-ids 1,2,3 \
  --max-new-tokens 3 --report-logits

# 同时比较 TP1、TP2 和 PP2（合成权重，不下载模型）
python -m benchmarks.qwen2_pp_compare_v047 \
  --dtype float32 --new-tokens 3 --output qwen2-v047-tp-pp.json

# 只执行定向测试
python -m unittest discover -s tests -p 'test_qwen2_pipeline_v047.py' -v
```

所有输出路径必须不存在，检查点来源必须是受信任本地目录。Stage 文件使用独立 SHA-256 和 Safetensors 加载；预检查失败将与另一 Rank 通过 Gloo readiness collective 协调退出。文件哈希说明字节未被运行前篡改，不等于原始发布商身份认证或对持续恶意节点的完整保护。

## 首次 GitHub Actions 实测（2026-11-10）

[真实 PP/TP 对照测试与已上传 JSON](https://github.com/tangxiang257-droid/opencompute-ai/actions/runs/42784462615) — 提交 `e0700b26` 对应的 CPU 完整回归与集群专项工作流均已成功，包括 TP1/TP2/PP2 的输出正确性、Rank 文件损坏拒绝和完整按层传递。测试为相同随机合成 Qwen2、FP32、4 层、生成 3 个 Token、同一 Linux CI 主机上的**单次**测量：

| 模式 | Rank0 decode 耗时 | Token/s | 相对单 Rank 速度 |
| --- | ---: | ---: | ---: |
| TP1 单 Rank | 10.53 ms | 285.023 | 1.00× |
| TP2 双 Rank 张量并行 | 22.96 ms | 130.678 | 0.459× |
| PP2 双 Rank 流水线并行 | 13.509 ms | 222.067 | 0.779× |

**结果解读**：这次 PP2 比 TP2 快，但仍比单 Rank 慢。三种模式均与单进程完整层参考的生成 Token 和 Logits 一致。PP2 没有做每层 All-Reduce，但仍需每个生成 Token 两次完整隐藏状态传递，阶段串行执行、Rank0 IO 汇总和等待仍是开销。以上数字不能用作跨网络、真实模型或稳定吞吐的性能保证。

此外，提交 `162fd5b3` 的 GitHub Actions <https://github.com/tangxiang257-droid/opencompute-ai/actions/runs/42784623965> 已显示**独立随机 HF Qwen2 完整模型与 PP2 的 FP32/BF16 对照步骤成功**。这个独立参照不使用与 OpenCompute 相同的前向计算实现，但依旧不是 DeepSeek-R1-Distill-Qwen-1.5B 官方完整权重的实测。

## 性能比较要求

与 TP 一样，记录每次样本的 rank0 Decode 时间、含进程初始化的总耗时、生成 Token/s、传输的逻辑激活字节数、Gloo send/recv wall time（**包含通信同步和等待，不是网卡实际传输字节**）及各进程的 Linux 峰值 RSS。

第一轮仅做单次 TP1/TP2/PP2 对照，应先得到全部 JSON 与通过的数值测试，之后再计划 3–5 次重复测量和更大模型。若 PP2 比 TP2 快，不能据此声称 PP 会改善互联网上的推理速度；若 PP2 比单 Rank 慢，也不表示 PP 的内存分布价值消失。

## 尚未实现的事项

- **没有公网或局域网独立设备之间的模型流水线**，Gloo 仍受 localhost 信任和进程配置限制。
- **没有集成原有 Worker 调度器或模型中心**；需要独立设计 PP worker capability、阶段资源匹配、安全分片分发、回滚与授权。
- **没有完整 DeepSeek-R1-Distill-Qwen-1.5B 真实预训练权重实测**。此 PP 原型虽然适用于完整 Qwen2 权重层计算，但 Rank 0 仍需完整 Embedding/LM Head；大模型容量仍受到该节点 IO 内存、磁盘和运行时开销约束。
- **没有并发 microbatch 流水线、断线恢复或跨设备链路加密**。单请求每 Token 分两次传递隐藏状态，尚不能证明吞吐优势。

这次的重点是给 PP 提供**可独立验证的可执行实现**，为后续比较和开发选择打基础。
