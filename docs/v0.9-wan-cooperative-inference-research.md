# OpenCompute AI v0.9 — WAN 协作推理研究与验收设计

- 日期：2026-11-12
- 状态：**设计稿 / 未部署 / 未声明性能收益**
- 目标：跨独立普通设备聚合可用模型权重容量；在实际测量支持时，优化同一次推理的延迟或多请求吞吐。
- 限制：不改变 v0.8.1 当前公网准入、管理员接口或正在运行的生产容器；本设计不能被视为公网推理已实现。

## 2. 现有代码审查与准确边界

- v0.8.1：公共 CUDA Worker 可以自动通过挑战加入、报告 GPU、领取有租约的矩阵校验白名单任务；公开 Worker **不能运行 Qwen2 生成任务**。依据：README.md、docs/v0.8.1-public-cuda-worker.md。
- v0.7：受信任 GPU Worker 能通过 GPU 队列执行整模型 Qwen2 生成，调度器已有显存预留和模型身份匹配；这一点不同于公开 Worker。
- v0.4.7/v0.4.8：Qwen2 双 Rank 本机 CPU Gloo 按层 PP、多个请求交错和分离 KV 已实现并有测试；**没有跨两台公网 GPU 连接**。
- v0.4.6：compute/parallel_screen_v046.py 仍是采用均匀节点、模型简单估算的旧版通信筛选；文件中的 PP “implemented: false” 指该历史阶段，不能代表今天所有版本没有本机 PP。
- 当前没有可信的真实 WAN TTFT、TPOT、P95、GPU VRAM 峰值或跨节点并行加速结论。
- 现有公网挑战与自报 GPU 不能证明物理设备真实性；矩阵校验也不能证明任意 Qwen2 推理输出正确。

## 3. 第一原则：对单请求延迟与服务吞吐分别建模

同一个 token 的不同 Transformer 层存在严格顺序依赖。两阶段 PP 能减少单节点模型内存负担，但不能让同一个 token 的前半层和后半层同时计算。多个独立请求、不同 token 阶段的流水线可以提升吞吐；单请求加速通常还需要局部 TP 或更细粒度算子并行，并受每层通信和同步开销限制。

示意：hidden=4096，BF16，每个 decode token 的一份完整激活约 8 KiB。若按本机 PP 原型，需要在每个生成步骤双向跨分片边界传输，则有约 16 KiB 的 payload。仅作理想化传输下界：40 ms RTT、20 Mbps 有效带宽时，网络约需要 40 + 16 KiB×8/20 Mbps ≈ 46.6 ms/token，尚未计入实际计算、排队、协议、丢包、控制消息和重传。任何实测值都必须标明是否包含 prefill。

## 4. v0.9 推荐架构

### 控制平面（现有 FastAPI + SQLite 可延续研究规模）

- ResourceProfiler：每个设备报告设备后端、显存可用量、Qwen2 已验证本机 prefill/decode 性能、算力负载、权重 SHA/模型 ID、可信等级。自报资料作为线索而非硬件证明。
- LinkProfiler：只有双方已明确同意的节点才执行有界、限速的 A↔B RTT、吞吐、抖动和丢包探测；不让匿名用户提供任意 URL 触发服务器内网扫描或 SSRF。
- ModelPlacementPlanner：先满足模型完整分片覆盖、显存及 KV/运行时预算；然后按实际层算力、网络和可靠性选择分片边界，输出 PP/TP/独立整模型三种候选的解释性理由。
- RequestRoutePlanner：模型放置是较慢周期决策，请求路由是快速决策；会话绑定模型版本、tokenizer、层范围与 KV 持有者；新请求可选新路由，运行中变更必须保证正确性。
- LeaseAndRecovery：保留租约、心跳、幂等完成和失败可追踪状态；故障时从可信 checkpoint/重算恢复，不能静默拼接旧 KV 和新模型版本。

### 数据平面（先受信任节点，后开放公网）

- 阶段 1：**两台独立物理设备**上的 Qwen2 PP；模型分片本地 SHA 校验、常驻模型实例、分片边界二进制传输、双向反馈、每请求专用 KV；先建立受认证和加密的端到端通道。
- 禁止将现有单机 Gloo rendezvous 或无认证张量端口直接暴露公网。可用受认证的出站连接和可信 relay 适配 NAT；先验证数据面连通和流量预算，再决定是否 P2P。
- 阶段 2：支持 N 阶段 PP、同局域网 TP 子组、跨地域 PP 组的**分层拓扑**。不应对所有公网设备直接使用每层 All-Reduce。
- 阶段 3：先评估无损激活压缩；低精度量化须有逐 token logits/输出准确性回归；再考虑多请求 microbatch 与推测解码。
- 阶段 4：多架构后端（CUDA 优先，ROCm/MLX 后续），模型适配与调度契约解耦；DeepSeek MoE 专家路由为后续独立里程碑，不视 Qwen2 密集模型实验为已支持 DeepSeek-V3。

### 安全域

- **trusted/private**：仅来自本人、已同意的实验机器；先执行可信 Qwen2 PP 验收。
- **public/verified-allowlist**：保持现有公网 CUDA 矩阵任务，不自动把陌生 Worker 升级为模型推理执行者。
- **public/inference-experimental**：必须在独立明确授权后引入；限制任务内容、输入尺寸、速率、会话及资源；风险提示包括请求内容、激活与 KV 可能泄露。未经验证不得宣传“私密推理”。
- 用户提交任务入口与设备贡献入口分离；普通用户不能获取管理员密钥、运行自定义 Python、上传可执行模型 pickle，或经 Worker 影响主机文件与网络。
- 对公网上不可信节点，错误结果检测不止 checksum：需要可信小样本复算、抽样冗余比对、故障注入测试及明确的信任/隐私策略；无法无条件保证所有推理结果无篡改。

## 5. 验收实验（严格将容量收益与速度收益分开）

### A：真实设备模型容量验收

1. 选择**实际开源发布的 Qwen2 小模型**和合法权重来源，不以合成权重代替最终验收；保留模型 ID、revision、sha256、tokenizer 和许可。
2. 两台独立机器，每台显存预算、层范围和权重 SHA 被记录；完整模型无法在单台实验机器给定内存预算中驻留，但两台分片成功；若可用也同时提供单机 CPU offload 对照。
3. Prompt/生成逐 token 与可信单机参考计算比对，检查 FP32/BF16 容差和输出一致性；报告每个设备峰值 VRAM/RSS、加载时间、KV 实际占用、掉线后状态。

### B：性能与路由验收

- 对每个方案记录至少多次重复样本和中位数、P95；冷热启动分别列出。
- 实测指标：TTFT、TPOT、Token/s（单请求）、requests/s（多请求）、prefill/decode 分时、P50/P95 RTT、有效带宽、单请求发送字节、GPU 利用率、VRAM/RSS 峰值、故障率与恢复时长。
- 场景：同机单 Rank 基线；同局域网双设备；跨公网双设备；不同显卡组合；网络限速 20/100 Mbps、RTT 5/40/100 ms、断连/丢包故障注入（限速测试只在允许的实验环境）。
- 成功判据：正确性先通过；容量实验能够超越单节点实际可驻留模型规模；只有同一模型、同一 prompt/token、同一硬件可比基线测得更好，才声明“加速”。预计达不到时自动选单机或其他可用路径。

### C：安全与自动接入回归

- 未认证公共 GPU 不能领取 Qwen2 Prompt；过期租约不能重复提交；断线和显存不足不能造成永久占用。
- 节点伪报 GPU/内存、恶意数据、重放请求、模型版本不一致、跨请求 KV 污染、连接指向内网等均有拒绝测试。
- 已有 CPU/GPU 队列、网页、管理员权限和 v0.8.1 公网准入回归全部保留，新增功能应由 feature flag 控制。

## 7. 特别针对当前项目的决策

1. 先不改变站点域名/备案中的部署。现有阿里云轻量服务器仍主要承担接入、API、调度、任务记录，不假定它有可用于大模型的 GPU。
2. 公共 GPU Worker 继续以矩阵验证为唯一公开白名单；真实推理从两台受信任设备起步。
3. 下一批代码应该从**最小性能探测器和两设备 Qwen2 分片传输**开始，而不是引入区块链、支付、自动任意代码执行、完全去中心化 DHT。
4. 发布前让控制台清晰区分“已接入 GPU”“可执行独立 GPU 任务”“已完成单机模型推理”“可协作模型分片”和“已验证加速”五种不同能力，禁止将节点数量或总 VRAM 相加伪装为已经可用的单模型显存。
