# OpenCompute AI v0.4.8 — 两阶段 Qwen2 流水线的多请求交错执行

## 交付范围

v0.4.7 的 PP 每次完整完成一条请求的两个阶段后才处理下一条请求。v0.4.8 新增一个**独立的、受信任本机的**多请求入口 `compute/qwen2_pipeline_batch_v048.py`，允许 Rank 0 通过 Gloo 非阻塞 `isend/irecv` 发送请求 A 的中间隐藏状态后继续计算请求 B 的前半层，Rank 1 处理 A 并异步返回，从而创造**真正阶段间重叠的机会**。

这不是在同一次前向中将 Token A 的两半层并行完成；它利用的是**不同请求之间的独立性**。同一请求仍必须顺序执行层依赖，且每个 Token 的计算结果返回后才能开始该请求下一 Token。正确性先于速度。

现有 `compute/qwen2_pipeline_v047.py`、Qwen2 TP、GPT-2、调度器和网站模型中心不被替换。此版的多请求 PP 没有接入现有调度器、没有独立设备通信，也不能用在公开的任意陌生节点上。

## Gloo 双 Rank 的实际执行顺序

```text
Wave: 两条请求 A 和 B，当前生成 Token 步骤 s

Rank 0（Embedding + 前半层 + LM Head）
  A: 前半层 -> isend(A), irecv(A 回传)
  B: 前半层 -> isend(B), irecv(B 回传)   [此时 Rank 1 可能处理 A]
  wait(A 完成), 生成 A 下一 Token
  wait(B 完成), 生成 B 下一 Token

Rank 1（后半层）
  recv(A), 后半层 A -> isend(A 回传)
  recv(B), 后半层 B -> isend(B 回传)
  等待发送句柄全部完成

所有请求进入下一轮 Token 步骤 s+1
```

两个 Rank 使用确定性的 `tag = 2 * (step * 4 + request_index)`，输出回传使用 `tag + 1`，请求顺序在 Rank 0 预检查后由同步长度向量指定。所有发出的张量缓冲区保持存活直到对应通信 Work 完成，避免异步发送与张量生命周期冲突。

**顺序模式**（`--mode sequential`）使用相同的两个 Gloo Rank、相同分块文件、相同 Token 步数、同一数量的请求、同一批 KV Cache，但每条请求直接 `send` → `recv` → 解码后才处理下一条；这样可以做执行方式的 A/B 对照。**交错模式**（`--mode overlap`）是新的默认值。真实是否有速度收益必须由两组 Decode/Token/s 的实测结果判断，不能把 `scheduling_opportunities` 计数冒充真实 CPU 计算重叠比例。

## 隔离与容量限制

1. **每条请求自己的 KV Cache**：两个 Rank 分别按请求 ID 对应的稳定索引持有该请求的层级缓存。Prompt 长度可以不同；每个请求 Token 进度不会交叉。
2. **最多 4 条活动请求**：这是本研究原型的固定容量，支持单条请求作为对照，但未实现网站上的动态接入队列、优先级、实时取消或流式响应。
3. **输入严格预检查**：每条请求有唯一的 `id`（1–32 位英数字及下划线、连字符），1–128 个有效 Token ID，模型的上下文窗口内完成；生成 Token 数是全局 1–8；输入 JSON 文件不得超过 8 KiB，不跟随软链接。
4. **显式 KV 预算**：`--max-kv-mib` 默认 64 MiB（可设置 1–4096 MiB），在两端进行理论峰值 KV 内存预算校验。该上限计入每请求每层 K/V、最大上下文与 `torch.cat` 的额外空间，任一 Rank 超额则双方协同拒绝执行。**这不是整个进程的物理 RSS 硬限制**，不包含 PyTorch、分块权重、其他 Python 结构或所有临时激活。
5. **权重缓存上限**：沿用原 `--cache-mib`，每个阶段的 LayerStream 与 Rank 0 的 ChunkedIO 分别拥有一个容量上限；它们不是相加后的全进程保证。
6. **失败安全**：任一 Rank 的输入、模型分片或理论 KV 预检查失败，都会通过 Gloo readiness Collective 拒绝启动 P2P 通信；中途的计算或设备故障仍可能依赖 Gloo 超时 / torchrun 进程终止，尚不是完善的分布式容错服务。

## 离线运行方法（不需要 DeepSeek 权重或云服务器）

先从已审核的本地 Qwen2 `opencompute-qwen2-tp-v2` 的 **单 Rank 分片目录**生成两阶段 PP Bundle（参见 `docs/v0.4.7-qwen2-pipeline.md`）。准备可信本地 JSON，例如：

```json
{
  "requests": [
    {"id": "alpha", "prompt_ids": [1, 2, 3]},
    {"id": "beta", "prompt_ids": [11, 4]},
    {"id": "gamma", "prompt_ids": [6, 7, 8, 9]}
  ]
}
```

```bash
# 使用已经存在的本地两阶段 Qwen2 PP 分片目录和请求 JSON
OMP_NUM_THREADS=1 python -m torch.distributed.run \
  --standalone --nproc-per-node=2 \
  -m compute.qwen2_pipeline_batch_v048 \
  --bundle /trusted/local/qwen2-pp \
  --requests-json /trusted/local/requests.json \
  --mode overlap --max-new-tokens 3 --max-kv-mib 64 \
  --report-logits

# 与严格顺序执行相比，运行随机合成小模型，不下载任何权重
python -m benchmarks.qwen2_multi_request_v048 \
  --requests 3 --repeats 2 --new-tokens 3 \
  --output qwen2-v048-batch-vs-sequential.json
```

后一个命令会生成可审核的 JSON：各模式的原始试验结果、总完成 Token 数/秒、中位数、最短/最长 Decode 时间、两端 P2P 逻辑张量字节、等待计时、Linux 单进程峰值 RSS 以及每条请求的完整 Token 输出。

**注意统计边界：** 两次重复测量不是统计显著性的保证。对照中的 `tokens_per_second` 是整批完成 Token 的吞吐量，不能用它冒充单条请求平均响应时间或公网真实吞吐量。Gloo 操作计时包含同步与等待，张量字节数不是网卡真实传输字节数。每一轮会启动新的 torchrun 进程组，并交替运行两种模式，以减轻部分执行顺序偏差。

## 专项测试与验收

- `tests/test_qwen2_pipeline_batch_v048.py`：验证请求数量、ID 去重、Prompt 边界、输入软链接、请求隔离、理论 KV 预算、最多 4 请求并发、相同模型独立稠密参考的逐 Token/Logits 一致性、错误输入使双方在 P2P 前拒绝，以及两种模式多轮数据结构。
- `tests/test_qwen2_pipeline_batch_hf_v048.py`：本地随机初始化、完全离线的独立 Hugging Face Qwen2ForCausalLM 验证 FP32 与 BF16 下三条不同 Prompt 的逐 Token/Logits 对照；CI 设置 `OPENCOMPUTE_REQUIRE_HF_TINY=1`，杜绝依赖缺失时默默跳过。
- GitHub Actions `.github/workflows/cluster-v03.yml`：运行专项检查并上传 `opencompute-qwen2-v048-multirequest` 性能报告 Artifact（7 天），仍运行之前的 CPU TP、PP、Worker、身份校验等回归测试。

只有对应提交的 GitHub Actions 显示成功，才称为该版本已通过完整验收。代码已经推送并不自动意味着无死锁、没有性能退化或能用于生产环境。

## 下一阶段

如果实测确实发现多请求吞吐改善，下一阶段应先完善有限队列的动态调度、公平性与请求超时，然后再尝试可信局域网双设备和真实模型。若没有改善，应改进分块权重缓存命中、预取、并行请求调度以及阶段划分，而不是声称“多设备一定更快”。
