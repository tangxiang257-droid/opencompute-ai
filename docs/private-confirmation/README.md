# Private explicit confirmation and C receiving assembly

Not mounted by default. No listener, model, GPU or node launcher is added. A trusted HTTPS host must authenticate the current user's session and provide `credential_for_scope`; the app never trusts a header as identity. Configure the actual SignedIdentityAdapter issuer/audience/public key and prepare LocalAdmission first. No resolver, issuer or valid current identity means deny. Tests use LAB keys and a synthetic scope resolver and do not establish a real human's consent.

Shortest usable workflow (trusted local composition):

1. Create the existing fresh consent service/reader and `ConfirmationApp(reader, identity_fence=..., origin=<fixed HTTPS origin>, credential_for_scope=<trusted session mapper>)`. The mapper returns only the authenticated current user's signed credential. Hosting, session establishment, TLS and reverse-proxy trust are prerequisites; no default mapper or public mount exists.
2. Use `app.consent.prepare(credential, declaration, policy, placements, receiver=...)` on the actual stored task. `receiver` strictly contains version=1, node, identity, purpose=result-store, storage_policy, retention_seconds (1..86400), max_charge_bytes. Confirmed byte allowance must cover payload plus 32768 manifest bytes, up to the existing 2MiB logical limit. Disk/DB/WAL/orphans and actual retention enforcement remain parent policy obligations, not covered by this number. This first increment requires exactly one token and C distinct from A/B; a three-token plan cannot authorize a one-token result.
3. Present `/confirm?id=<proposal>&digest=<digest>`. GET reads the server-side full task/source/plan/budget/privacy/expiry/A/B/C body, HTML-escaped, no-store and non-frameable. GET does not activate. A same-origin POST with the reviewed, credential-bound one-use challenge and explicit Confirm records ACTIVE through the existing TaskConsent.confirm transaction. Cancel/revoke uses TaskConsent.revoke, including pending/active requests; authenticated historical GET is not restored eligibility. Missing/expired identity, changed body/digest, CSRF origin, repeated challenge or unknown confirmation refuses. No lock spans ASGI reads/writes. Challenge state is bounded, transient UI state, never a new grant table.
4. Continue the same `app.consent` through existing `IssuanceConsent`/RegisteredInputSource and runtime parent permission providers. A confirmed record alone is not permission from those parents. Stored input, confirmation receipt and history never become execution credentials. Old bodies retain their old canonical bytes and have no implicit C authority.
5. For C **in the same process as this consent authority**, call `await ReceiverConsent.create(app.consent, credential, proposal_id, digest, actual_B_spec, receive_binding, parent=<genuine C policy>)`, then `view.ingress(reader, writer, TLSConfig, metadata_channel, receive_binding, identity=<real peer identity>, authorize=<real transport policy>)`. This constructs the actual existing ResultIngress with the receiving view; no separate receive protocol. The factory binds the actual supplied writer's TLS generation; metadata must match that generation, exact input list and full binding. C parent receives confirmed C terms and must attest its own local identity/storage/retention/capacity and original connection, not reuse B permission. Its synchronous context must yield None and cannot suppress failures. One view qualification per proposal/boot, one ingress claim; failure does not restore them.
6. Existing `ResultIngress.receive` remains the payload/manifest reservation and persistent publication path with its own permission/resource checks. This increment does not bypass v12/v13 plan/execution bans to demonstrate a result. The tests exercise actual confirmation transactions, actual C ingress construction and real Channel metadata over memory streams; they do not show a complete authorized computation-to-publication chain.

The new receiving view is local and non-portable. A remote C still needs a genuine remote authorization/revocation mechanism; copying the SQLite database, consent receipt or Python fields cannot serve as that mechanism. Shared local claim/revocation state is not a global anti-replay service. Restart cannot reconstruct ACTIVE eligibility from history. v12/v13 execution bans remain; no testing permit is installed into production.

Revocation cannot unsend a rendered page/frame or undo an earlier commit. A user/parent fence exit error after side effects makes the outcome uncertain and retires the receiving view, not a successful rollback. Provider absence, unknown resource state and absent actual device-completion evidence keep real execution denied. Retention terms are consent constraints, not proof of an implemented deletion scheduler.
