# OpenCompute AI v0.7.1 — GPU task scheduling

## What this phase adds

- A separate, allowlisted GPU task queue with one fixed workload: matmul_checksum.
- Per-GPU VRAM reservations with transactional, serialized claims.
- CUDA-runtime-aware placement. A GPU is schedulable only when the Worker reports a usable PyTorch CUDA runtime.
- Lease expiry, offline Worker recovery, retry/cancel, and token-checked completion.
- Administrator-only task submission and status; node-token-only Worker claim/completion.
- A dashboard form and task table for submitting and monitoring GPU tasks.

## API

- POST /v0.7/gpu-tasks — submit an allowlisted GPU matrix checksum task.
- GET /v0.7/gpu-tasks — list recent tasks and lifecycle counters.
- POST /v0.7/nodes/{node_id}/gpu-claim — claim a GPU task with X-Node-Token.
- POST /v0.7/gpu-tasks/{task_id}/complete — submit a result with node token, assigned GPU index, and lease token.
- POST /v0.7/gpu-tasks/{task_id}/cancel and /retry — administrator recovery controls.

## Placement and reservation rules

The scheduler requires a fresh node heartbeat, fresh GPU telemetry, NVIDIA/CUDA
backend, and a Worker-reported pytorch_cuda runtime. The Worker maps nvidia-smi
physical devices to PyTorch logical CUDA indices by UUID, with a unique-name
fallback; ambiguous mappings are marked non-schedulable to avoid running a task
on a different GPU than the one whose VRAM was reserved. It computes available
memory from the latest free-memory snapshot minus active reservations created
after that snapshot. A later GPU telemetry report supersedes older reservations
because the measured free-memory value then reflects the running workload.
Claims and reservation writes occur under one SQLite BEGIN IMMEDIATE
transaction, preventing two Workers from allocating the same remaining VRAM.

The runtime marker and GPU metrics remain self-reported telemetry, not hardware
attestation. The scheduler is a trusted-network research feature, not a public
anonymous compute marketplace.

## Worker requirements

The existing CPU-only Dockerfile.worker intentionally does not bundle CUDA or
PyTorch. To run GPU tasks, install the project requirements with a PyTorch build
compatible with the host NVIDIA driver, confirm torch.cuda.is_available(),
and run python -m cluster_v03.worker on the host. Containerized GPU workers
must separately install a compatible CUDA-enabled PyTorch build and be launched
with NVIDIA Container Toolkit GPU access.

## Current limitations

This is a bounded GPU scheduling and execution proof, not model inference,
multi-GPU tensor parallelism, cross-device VRAM pooling, trusted hardware
attestation, or internet-facing Worker admission.
