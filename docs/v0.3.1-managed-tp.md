# OpenCompute AI v0.3.1 — 注册节点协同 GPT-2 张量并行（仅限本机实验）

本阶段把 **v0.3 节点注册/心跳/能力上报** 与 **v0.2 的 GPT-2 张量并行引擎** 连起来。使用真正独立运行的 CPU Worker 进程和 PyTorch Gloo，而不只是排队执行普通 `sum` 任务。

**已验证范围：** 一个受信任 Linux 主机上的两个独立 HTTP Worker 进程，完成注册、能力选择、分片下载、SHA-256 验证、模型格式检查、全员准备屏障、实际 Gloo 推理、结果上报，并与独立 dense GPT-2 参考结果对照。

**未实现：** 跨物理主机自动启动、家用宽带公网部署、TLS / mTLS、可信执行环境、GPU 显存池、互联网节点故障容错、第三方节点安全隔离。此版本的 Gloo `MASTER_ADDR` 固定为 `127.0.0.1`，**必须是同一台主机**。不要把它描述成已支持跨设备公网联合推理。

## 1. 不购买服务器的最简联调

从仓库根目录运行：

```bash
python -m pip install -r requirements.txt
python -m pip install 'httpx>=0.27,<1'
python -m unittest discover -s tests -p 'test_tp_v031.py' -v
python -m benchmarks.tp_session_demo
```

`benchmarks.tp_session_demo` 自动在本机随机端口启动一个私有 FastAPI 服务和 2 个新 Worker，生成独立的临时 Admin/Join Key，创建合成 GPT-2 会话，完成分片与推理，并退出和清理本地进程。无需下载预训练权重。**本机模拟两个 Worker 并不等于拥有两台物理设备**。

## 2. 手动运行持久服务

在第一个终端设置两个不同的、至少 16 字符的随机密钥：

```bash
export OPENCOMPUTE_ADMIN_KEY="$(python -c 'import secrets;print(secrets.token_urlsafe(32))')"
export OPENCOMPUTE_JOIN_KEY="$(python -c 'import secrets;print(secrets.token_urlsafe(32))')"
export OPENCOMPUTE_DB_PATH="./.opencompute/cluster.sqlite"
export OPENCOMPUTE_TP_ROOT="./.opencompute/tp-sessions"
export OPENCOMPUTE_TP_CHECKPOINTS="./.opencompute/checkpoints"
uvicorn backend.app:app --host 127.0.0.1 --port 8000
```

在另外两个终端设置**相同的 Join Key**，分别启动独立 Worker：

```bash
# Worker A
python -m cluster_v031.worker --url http://127.0.0.1:8000 --name cpu-a --cache .opencompute/worker-a --once

# Worker B
python -m cluster_v031.worker --url http://127.0.0.1:8000 --name cpu-b --cache .opencompute/worker-b --once
```

在第四个终端使用 Admin Key 启动受控实验：

```bash
curl -X POST http://127.0.0.1:8000/v0.3.1/sessions/synthetic \
  -H "X-Admin-Key: $OPENCOMPUTE_ADMIN_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"workers":2,"hidden":16,"heads":4,"layers":2,"prompt_ids":[1,2,3],"max_new_tokens":3}'
```

记录返回的 `session_id`，随后查看：

```bash
curl -H "X-Admin-Key: $OPENCOMPUTE_ADMIN_KEY" \
  http://127.0.0.1:8000/v0.3.1/sessions/SESSION_ID
```

预期状态依次为 `preparing → running → completed`；失败为 `failed`。Rank 0 的 `result.generated_ids` 是合成权重模型的 token ID，不是自然语言文本。

## 3. 已导出 GPT-2 权重的可信本地加载

如果已有**你信任的、预先导出**的 GPT-2 TP 检查点（不允许来自用户提交的任意 URL），将完整文件夹放在服务端的 `OPENCOMPUTE_TP_CHECKPOINTS` 下。每个检查点必须有 `manifest.json`、`rank_0.pt`、`rank_1.pt` 等以及 `rank0_io.pt`。文件最大允许 512 MB / 个，最多 4 rank。

例如在可信网络环境中安装 `transformers` 后，执行此前的导出器：

```bash
python -m pip install 'transformers>=4.48,<5'
python -m compute.gpt2_shards --model sshleifer/tiny-gpt2 \
  --output .opencompute/checkpoints/tiny-gpt2 --workers 2
```

再调用：

```bash
curl -X POST http://127.0.0.1:8000/v0.3.1/sessions/checkpoint \
  -H "X-Admin-Key: $OPENCOMPUTE_ADMIN_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"checkpoint":"tiny-gpt2","prompt_ids":[15496,995],"max_new_tokens":3}'
```

服务端只接收受限的**目录名**，不是任意磁盘路径。导出器可以在离线情况下使用本地可信模型目录；系统不会为了会话接受远程下载地址。

## 4. 调度与授权流程

1. Worker 通过 v0.3 Join Key 注册，声明 `tp_gpt2` 能力，并上报 CPU/内存及性能评分。
2. 管理端提交 GPT-2 TP 会话。调度器筛选在线、空闲、具备能力且内存估算满足要求的不同节点。
3. 会话在 SQLite 中持久化为各 Node ID 对应的 rank。管理员不能让普通 Worker 请求不属于自己的 shard。
4. Worker 携带**自身的** `X-Node-Token` 下载 `manifest.json` 和 `rank_N.pt`；只有 rank 0 另外拿到 `rank0_io.pt`。使用 SHA-256、大小和权重形状进行校验。
5. Worker 报告 `ready`；所有参与者就绪后，协调器设置 `running`。
6. 各 Worker 使用受限固定入口 `python -m compute.gpt2_generate`、`RANK/WORLD_SIZE/MASTER_ADDR/MASTER_PORT` 启动独立进程；PyTorch Gloo 执行同一次模型前向中的 All-Reduce。
7. 两个 rank 完成后上报结果，会话进入 `completed`，否则进入 `failed`。准备阶段超时、运行阶段超时或 Worker 心跳丢失均可触发失败。

此处的“预热”是将权重**下载到 Worker 本地磁盘、校验并尝试加载**，然后由实际 Gloo 子进程重新加载。它不是 GPU VRAM 中永久保留的已加载模型。

## 5. 当前限制与下一阶段

- 只允许一个运行中 TP 会话；一个 Worker 不得同时参与两个 TP 会话。没有抢占式重调度。
- 内存筛选依据 Worker **自报的可用 RAM** 加上估算的 128 MiB 运行开销；不是实际内存隔离或防作弊机制。
- Worker 持有共享 Join Key，尚无服务端证书校验、签名、独立节点准入或代码沙箱。**禁止开放至公网、不接受陌生设备**。
- 会话在错误后不做安全重试。分布式 Gloo 进程成员不可在一次前向计算中透明替换；下一步需要运行组重建及任务级重试。
- 跨主机版本将需要专用私有网络/隧道、受限端口与明确的 rendezvous 主机，而不是简单把 `127.0.0.1` 换成公网 IP。
- 模型分片的加载与生成可运行于本机不同进程；并未实现智能设备使用量计费或 GPU 算力池。
