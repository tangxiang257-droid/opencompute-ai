# OpenCompute AI v0.5.0 — 动态请求队列接入 Qwen2 双阶段推理

## 本阶段目标

v0.4.9 的 FairRequestQueue 不再只是独立调度原语。v0.5.0 新增 cluster_v05.Qwen2PipelineService 和 /v0.5 HTTP 路由，把动态到达的 API 请求交给公平队列，再将最多 4 条请求组成一个 microbatch，交给已验证的 v0.4.8 两阶段 Qwen2 Gloo 推理引擎。

当前服务是**真实推理路径的第一版整合**，但仍是可信本机 CPU 实验服务，不是公网多租户平台。

## 请求路径

1. API 验证管理员凭据、客户端标识和 Token ID 列表。
2. FairRequestQueue 负责全局容量、单客户端配额、客户端间 Round-Robin、请求截止时间和安全关闭。
3. 一个有界消费者收集最多 4 条请求；同一客户端 FIFO，不同客户端轮询。
4. 服务为 microbatch 写入权限为 0600 的临时 JSON 文件。
5. 启动两个本机 Gloo Rank，执行 compute.qwen2_pipeline_batch_v048 的真实 Qwen2 PP。
6. Rank 0 输出 JSON 结果，服务按 request ID 对齐结果并逐个完成 Future。
7. 队列满时返回 HTTP 429；排队/执行超时返回 HTTP 504；推理进程异常返回 HTTP 503。

## 重要实现边界

- 每个 microbatch 会启动一个新的 torch.distributed.run 双进程组。模型权重会随批次重新加载；这会增加启动和权重读取开销。v0.5.0 的重点是验证**动态 API → 公平队列 → microbatch → 真正两阶段 Qwen2 推理 → HTTP 结果**闭环，不宣称已经具备常驻高性能推理服务。
- 单个服务实例只有一个队列消费者和一个活动 PP microbatch，避免多个请求组争抢同一组设备/端口。并发容量通过队列背压控制，而不是并行启动任意多个 torchrun。
- 一个 microbatch 使用同一个 max_new_tokens，由服务配置统一指定；不同请求的 Prompt 长度可以不同。
- 每个请求有端到端截止时间；若批次执行超过最早请求剩余时间，当前 microbatch 会被终止，批次中未完成的请求都会收到错误。
- 请求取消、流式 Token、持久 Gloo 进程组、跨服务实例协调和自动设备故障恢复尚未实现。
- X-Client-ID 当前只是用于公平调度的客户端分组标识，调用方可以伪造。API 仍要求管理员密钥；这不是生产级用户身份认证或公网安全边界。
- 模型 bundle 必须是服务端预先准备并信任的本地目录。客户端不能指定模型路径、命令或 Worker 地址。
- 两个 Gloo Rank 都在同一台主机运行。这里没有真实跨设备网络传输，也没有把本机 CPU 测试描述成多台个人设备的实测加速。

## 启动方式

先按 docs/v0.4.7-qwen2-pipeline.md 准备已经导出的两阶段 Qwen2 PP bundle。然后配置环境变量：

    export OPENCOMPUTE_ADMIN_KEY='至少 16 位的随机管理密钥'
    export OPENCOMPUTE_JOIN_KEY='至少 16 位的随机节点加入密钥'
    export OPENCOMPUTE_QWEN2_PP_BUNDLE='/trusted/local/qwen2-pp'
    export OPENCOMPUTE_QWEN2_PP_MAX_NEW_TOKENS=3
    export OPENCOMPUTE_QWEN2_PP_MAX_KV_MIB=64
    export OPENCOMPUTE_QWEN2_PP_MAX_PENDING=128
    export OPENCOMPUTE_QWEN2_PP_MAX_PENDING_PER_CLIENT=16
    export OPENCOMPUTE_QWEN2_PP_MAX_BATCH_SIZE=4
    export OPENCOMPUTE_QWEN2_PP_BATCH_WAIT_MS=12

    python -m uvicorn backend.app:app --host 127.0.0.1 --port 8000

默认入口同时提供模型中心控制台：

    http://127.0.0.1:8000/v0.4/console

也可使用轻量研究入口 `cluster_v031.local_server:app` 提供 API，但它不托管模型中心 HTML 页面。

未配置 OPENCOMPUTE_QWEN2_PP_BUNDLE 时，/v0.5/status 会报告 disabled，/v0.5/requests 返回 HTTP 503；不会偷偷退回到合成模型或其他引擎。

## Docker Compose（可选）

仓库根目录的 `Dockerfile` 默认启动 `backend.app:app`，因此同样包含模型中心和 v0.5 API。默认 Compose 配置只绑定到本机 `127.0.0.1:8000)，并且**不会自动启用 Qwen2**。

要启用已准备好的本地 PP bundle，在 `docker-compose.yml` 旁创建 `docker-compose.qwen2.override.yml`：

    services:
      opencompute:
        environment:
          OPENCOMPUTE_QWEN2_PP_BUNDLE: /models/qwen2-pp
        volumes:
          - /absolute/path/to/qwen2-pp:/models/qwen2-pp:ro

将宿主机路径替换为真实 bundle 目录，再启动：

    OPENCOMPUTE_ADMIN_KEY='至少 16 位的随机密钥' \
    OPENCOMPUTE_JOIN_KEY='至少 16 位的随机密钥' \
    docker compose -f docker-compose.yml -f docker-compose.qwen2.override.yml up --build -d

不要把模型权重复制进 Docker 镜像；使用只读挂载。若没有 bundle，保留默认配置即可，Qwen2 队列会明确显示 disabled。

## HTTP 请求

    curl -X POST http://127.0.0.1:8000/v0.5/requests \
      -H 'Content-Type: application/json' \
      -H 'X-Admin-Key: YOUR_ADMIN_KEY' \
      -H 'X-Client-ID: local-user-a' \
      -d '{"prompt_ids":[1,2,3,4]}'

响应包含 request_id、generated_ids、engine、model、batch_size 和批次耗时。Prompt 需为 1–128 个非负整数 Token ID；实际词表和上下文长度由 Qwen2 bundle 的预检查决定。

管理员可通过：

    curl http://127.0.0.1:8000/v0.5/status \
      -H 'X-Admin-Key: YOUR_ADMIN_KEY'

查看队列长度、活动请求、批次数、成功/失败数和最近错误。

## 验收

- tests/test_qwen2_live_service_v050.py：验证动态批处理、Round-Robin 公平性、队列背压、执行错误传播、服务恢复、HTTP 管理员认证和输入校验。
- OPENCOMPUTE_REQUIRE_LIVE_PP_V050=1 时，专项集成测试会生成完全离线的 Qwen2 随机权重，准备两阶段 bundle，向真实 HTTP 服务同时提交三个请求，并通过两个真实 Gloo CPU Rank 执行推理；每个输出 Token 与独立稠密参考对照。
- GitHub Actions 必须成功，才可称为 v0.5.0 通过验收。

## 后续优化

v0.5.1 的首要工作是将“每批启动一次 torchrun”改为**常驻双 Rank 推理进程组**，让模型权重只加载一次，并通过控制通道动态接收 microbatch；之后再把 Rank 进程从 localhost 扩展为可信局域网 Worker。公网设备接入必须另行设计身份、密钥轮换、传输加密、模型分片校验、资源隔离和故障恢复。
